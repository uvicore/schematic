# 2026-08-31

## Document the PlanetScale/Vitess handshake autocommit change in the MySQL connection stub

- **Intent:** PlanetScale is changing Vitess to report the correct autocommit value in the initial
  handshake packet (rolling out **2026-09-01**). Vitess previously reported it wrongly, so
  pymysql/aiomysql/asyncmy connections ran with autocommit effectively **ON** despite the driver
  intending OFF. After the change those connections become autocommit=False, leaving an implicit
  transaction open on every connection — which Vitess aborts after 20 seconds. Any Uvicore app
  generated from this schematic and pointed at PlanetScale hits this.
  <https://planetscale.com/docs/vitess/connecting/pymysql-handshake-autocommit>

- **Changed:** added a **commented** PlanetScale example to the MySQL connection stub's `options`
  examples in `acme/appstub/config/database.py`, alongside the existing pymysql/aiomysql SSL
  examples. It shows `{'ssl': True, 'autocommit': True}` and explains why. No framework change was
  needed — uvicore's `options` is already a straight passthrough to SQLAlchemy's `connect_args`
  (`uvicore/database/db.py::init`), which is exactly the shape PlanetScale's own SQLAlchemy example
  uses.

- **Why commented, and NOT shipped as an always-on `True` default** — the tempting idea was "it's
  True by default anyway, so just make it explicit." **It is not.** Measured, not assumed:
  - `pymysql.Connection` and `aiomysql.Connection` both declare `autocommit=False` as their default.
  - Against a real MySQL with no `autocommit` kwarg, the live session reports
    `@@session.autocommit = 0`.
  - It only *looks* True on PlanetScale today **because of the very handshake bug being fixed**.

  So hardcoding `True` in the stub would not surface an existing default — it would **change** the
  default for every generated app on ordinary MySQL/MariaDB. And that change is not cosmetic:
  measured against a live MySQL, `INSERT` → `conn.rollback()` leaves the row **committed** under
  forced `autocommit=True`, versus correctly rolled back with the driver default. Silently disabling
  rollback for every new app is a far worse failure mode than a PlanetScale user missing a config
  line, so the stub documents it and explicitly warns against copying it onto non-PlanetScale
  connections.

- **Files:** `acme/appstub/config/database.py`.

- **Related:** `dataplatform/data-audit-uvicore-app` applied the real fix to its three
  PlanetScale-capable connections the same day (its `journal/2026-08-31.md`), scoped deliberately to
  exclude its Aurora and its write-target MySQL connections for exactly the rollback reason above.
